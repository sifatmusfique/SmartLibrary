1.3 Student & Teacher Queries — Answered by ID 252311282

Q1 (Teacher): Why did you use a raw Bounded Array instead of std::vector or a Linked List for the Book Catalogue?
Answer: Per the CSE 2103 rubric, ready-made STL containers like std::vector are prohibited. A manual raw array (new Book[capacity]) stores books in contiguous memory, makes slot indexing [0..count-1] instant, and lets us demonstrate manual left-shifting during deletion and Rule-of-Five memory cleanup in our destructor.
Q2 (Student): What happens to the array slots [0], [1], [2] on the website if I delete book [0]?
Answer: In BookCatalogue::remove(), every book after the deleted index shifts one position left (m_books[i] = std::move(m_books[i+1])) and m_count decreases by 1. On the website table, you immediately see the remaining books slide up into slot [0] so there are never empty holes inside the active prefix.
Q3 (Teacher): Why can't we toggle a book from "Available" to "Borrowed" inside the Edit Book modal?
Answer: Allowing arbitrary status toggles in the UI would corrupt circulation consistency—there would be no Borrow/Return history node or Return Stack update. So editMetadata() only edits Title and Author, while availability only changes through controlled borrowBook(), returnBook(), and processNextRequest() calls.
Q4 (Student): Why can't I delete a book that says "Borrowed" or has someone waiting in the queue?
Answer: LibraryManager::deleteBook() explicitly returns Status::Blocked if !book.available or m_requestQueue.contains(id), preventing orphaned requests in the queue or deleting a book that hasn't been returned yet.

Borrow/Return Circulation, Return Stack (LIFO) & History (Singly Linked List)

Explains circulation state transitions, LIFO stack operations, linked-list nodes, and failure atomicity
"Hello, my ID is 252311284. Next, I will demonstrate what happens when users click Borrow, Queue, and Return on our website, and explain the two green and purple panels: the Recent Returns Stack (LIFO) and the Borrow/Return History (Singly Linked List)."

2.1 How Borrow & Return Work Across Multiple Structures

  • Clicking "Borrow" on an Available Book: Calls LibraryManager::borrowBook(id). It marks the book Borrowed in the Array Catalogue and appends a yellow BORROW node to the History Linked List with a unique Tx#.
  • Clicking "Queue" on an Already-Borrowed Book: The same borrowBook(id) function sees available == false. It does not touch History or Catalogue status—instead, it calls RequestQueue::enqueue(id) and updates the banner to "Book is already borrowed. Request added to queue."
  • Clicking "Return" on a Borrowed Book: Calls LibraryManager::returnBook(id). It marks the book Available, pushes the book ID onto the top of the Return Stack, and appends a green RETURN node to the History Linked List.

2.3 Failure Atomicity (Why State Never Gets Half-Updated)

Before borrowBook or returnBook changes the Catalogue status or pushes to the Stack, LibraryManager first calls m_history.prepareAppend(...) inside an RAII PendingNode handle. If memory allocation fails (std::bad_alloc, verified in test T33), no book status, stack item, or transaction counter is modified. Only after all checks pass does commitAppend() link the node at m_tail in noexcept O(1) time.

2.4 Student & Teacher Queries — Answered by ID 252311284

Q1 (Teacher): Why did you choose a LIFO Stack for Recent Returns and reject returns when the Stack is full?
Answer: Returned books pile up on a desk in Last-In, First-Out order—the last book dropped off is on top (offset 0) for reshelving. If m_returnStack.isFull(), returnBook() rejects with Status::Full so we never lose a return record or desynchronize the stack from the catalogue.
Q2 (Teacher): Why does HistoryList keep a m_tail pointer in addition to m_head?
Answer: Without m_tail, appending a new transaction at the end of the linked list would require walking all h existing nodes (O(h)). Keeping m_tail gives us constant-time O(1) chronological append while still allowing full traversal from m_head.
Q3 (Student): If I delete a book from the Catalogue, why does its card stay visible in the History chain?
Answer: Each HistoryRecord stores an independent snapshot (transactionId, bookId, title, action). Deleting an available book removes it from active inventory, but historical audit logs remain readable (verified by test T20).
Q4 (Teacher): How do you prevent memory leaks in your Singly Linked List?
Answer: Every node is allocated exclusively by HistoryList. Our destructor calls clear() to walk and delete every node, and we implemented the full Rule of Five (with exception-safe deep copying inside try/catch) so copying never creates dangling pointers.

3.3 Student & Teacher Queries — Answered by ID 252311285

Q1 (Teacher): Why use a Circular Array Queue instead of a regular linear array queue, and how do you distinguish Full from Empty?
Answer: In a linear array queue, dequeuing from the front wastes earlier slots or forces O(q) shifting. Our Circular Queue wraps around using modulo arithmetic (m_front + offset) % m_capacity so enqueue and dequeue stay O(1). Tracking m_count explicitly distinguishes Empty (m_count == 0) from Full (m_count == m_capacity) without wasting a sentinel slot—so even capacity = 1 works.
Q2 (Teacher): If the book at the front of the queue is still borrowed, why doesn't "Process FIFO Head" skip to the second request?
Answer: Skipping the front request would violate strict FIFO fairness. Instead, processNextRequest() reports Status::Blocked and leaves the queue intact. If the librarian wants to clear a blocked head request, they explicitly click Cancel Head Request.
Q3 (Student): In the Maintenance Console, why doesn't changing a History action from BORROW to RETURN make the book Available?
Answer: As required by the design contract, the Maintenance Console only corrects educational log text (title and BORROW/RETURN label) or fixes slot IDs—it never bypasses circulation rules or mutates live book availability.
Q4 (Teacher): What do "Top Offset" and "Front Offset" mean in Stack and Queue maintenance?
Answer: Offset 0 always means the logical front/top! On the Stack, topOffset = 0 maps to physical index m_count - 1. On the Circular Queue, frontOffset = 0 maps to physical index (m_front + 0) % m_capacity. When updating a slot, LibraryManager first checks that the new Book ID exists in BookCatalogue so invalid IDs can never enter the stack or queue.
