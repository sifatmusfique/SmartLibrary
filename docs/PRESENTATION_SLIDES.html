Problem Statement & Real-Life Relevance

Why a Library Needs Four Different Data Structures

A real library handles four distinct workloads. No single linear structure performs well for all four simultaneously, so our system assigns each task to the structure that models it best:

1. Book Inventory

Bounded Array
Stores unique-ID books in contiguous slots [0..count) for fast traversal and dense storage.

2. Transaction Log

Singly Linked List
Grows chronologically with every borrow/return without shifting existing records.

3. Return Desk

Bounded Stack (LIFO)
Tracks recently returned books where the latest return sits on top for inspection.

4. Waiting Line

Circular Queue (FIFO)
Serves waiting borrowers fairly in exact request order when a book is unavailable.

Why Each Structure Was Selected Over Alternatives

Component Selected Structure Alternative Considered Technical Justification
Catalogue
BookCatalogue		 Bounded Raw Array (Book*) Linked List / BST Contiguous memory with zero per-node pointer overhead for a bounded 100-book shelf; cleanly demonstrates dense left-shift deletion in O(n).
History
HistoryList		 Singly Linked List (head + tail) Dynamic Array / Doubly Linked List O(1) chronological tail append with zero array reallocation or shifting; only forward chronological traversal is needed, saving a prev pointer per node.
Recent Returns
ReturnStack		 Bounded Array Stack (int*) Queue / Linked Stack LIFO matches physical desk stacking (last returned = top); array backing avoids per-push heap allocation and demonstrates overflow/underflow clearly.
Waiting Requests
RequestQueue		 Circular Array Queue (int*) Linear Array Queue Linear array queue wastes vacated front slots or forces O(q) shifting; circular modulo indexing (front + count) % cap keeps enqueue/dequeue O(1).

System Design & Architecture

Layered Architecture & Failure Atomicity

  • Failure Atomicity: borrowBook, returnBook, and processNextRequest pre-allocate HistoryList::PendingNode before changing book status, stack, or queue—if allocation fails, zero state changes occur.
  • Strict Invariants: Cannot delete borrowed/queued books; cannot return when stack is full; Maintenance edits never alter live availability.

Limitations & Conclusion

Current Limitations, Future Improvements & Questions

Honest Current Limitations

  • Volatile Storage: Data stays in RAM and resets on exit (no database or file persistence per course scope).
  • Fixed Array Bounds: Catalogue, Stack, and Queue default to 100 slots.
  • No Member Accounts: Requests store Book ID only; repeated requests are allowed.

Future Extensions

  • File / SQLite persistence & student account authentication.
  • Due dates, fine calculation, and multi-copy book counts.
  • Hash table or BST indexing for O(1) / O(log n) catalogue lookup.
